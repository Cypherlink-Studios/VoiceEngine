# voice-backend-sfu Specification

## Purpose
Provides real-time WebRTC media routing, token validation, dynamic proximity culling, and plugin telemetry synchronization for spatial voice chat.

## Requirements

### Requirement: WebRTC SFU Media Routing
The voice backend SHALL manage WebRTC transports and audio streams using Mediasoup, receiving single upstream microphone tracks and selectively routing downstream audio based on proximity.

#### Scenario: Audio producer transport establishment
- **WHEN** an authenticated web client requests an upstream audio transport
- **THEN** the SFU SHALL initialize a WebRTC transport and register an audio producer for the client's Opus microphone stream.

#### Scenario: Dynamic downstream consumer subscription
- **WHEN** another player enters within audible proximity of a listener
- **THEN** the SFU SHALL establish an audio consumer to forward the nearby player's audio stream to the listener's web client.

#### Scenario: Inaudible player unsubscription
- **WHEN** a speaking player moves beyond the maximum voice radius of a listener or leaves the dimension
- **THEN** the SFU SHALL close or pause the downstream consumer to conserve client and server network bandwidth.

### Requirement: Spatial Proximity Culling and State Dispatch
The server SHALL evaluate player Euclidean distances and dimensions from plugin telemetry at each tick cycle, updating audio routing and dispatching relative spatial positions to listening clients.

#### Scenario: Inter-dimensional isolation
- **WHEN** two players are in different Minecraft worlds (e.g. Overworld vs Nether)
- **THEN** the backend SHALL prevent any audio forwarding between them regardless of numeric coordinate proximity.

#### Scenario: Sneaking whisper attenuation
- **WHEN** a player speaks while sneaking
- **THEN** the server SHALL reduce their effective broadcast radius from the standard distance (30 blocks) to the whisper distance (8 blocks).

#### Scenario: Environmental submersion flagging
- **WHEN** a player's telemetry indicates they are underwater
- **THEN** the backend SHALL include the submerged environmental state flag in spatial updates sent to connected peers.

### Requirement: Plugin WebSocket Control and Token Verification
The backend SHALL host an authenticated WebSocket control endpoint for the Paper plugin to exchange session tokens and player positional batches.

#### Scenario: Plugin handshake authentication
- **WHEN** a Paper plugin connects to the control endpoint presenting the configured secret key
- **THEN** the backend SHALL accept the connection and begin ingesting positional batch frames.

#### Scenario: One-time token redemption
- **WHEN** a web client attempts to join with a temporary token generated by the plugin
- **THEN** the backend SHALL authenticate the session, link it with the player's Minecraft UUID, and consume the token so it cannot be reused.
